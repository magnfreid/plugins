Claude Instructions — SwiftUI Boilerplate

This file is read by AI assistants working in this project. Follow these instructions to maintain consistency with the established architecture.

Project Overview

This is a SwiftUI boilerplate / starter template targeting iOS 17.0+. It uses no external packages — Apple frameworks only. The project is structured so that optional modules (SwiftData, networking, etc.) can be deleted with minimal side effects.

Architecture Rules

State management

Use @Observable for all stores. Do NOT use ObservableObject or @Published.
Global/shared state lives in Stores/. These are injected into the environment in App/swift_ui_boilerplateApp.swift.
Local view state uses @State only.
Do NOT use singletons for stores.
Add a view model class (@Observable) only if a view has complex, view-specific logic that doesn't belong in a store. When you do, inject it via .environment(), not as a direct @State on the view.
Adding new stores

Create StoreName.swift in Stores/.
Mark it @Observable final class.
Instantiate it with @State private var storeName = StoreName() in the App entry point.
Inject it with .environment(storeName).
Access it in views with @Environment(StoreName.self) private var storeName.
Adding new features

Create a new subfolder inside Features/, e.g. Features/Profile/.
Place ALL views for that feature inside it. No view code belongs outside Features/ — not even in App/. App/ contains only swift_ui_boilerplateApp.swift (the @main entry point) and AppRouter.swift (not a view).
Add the destination to AppDestination in App/AppRouter.swift.
Add a navigationDestination case in the NavigationStack inside Features/Root/MainTabView.swift.
Navigation

AppRouter is @Observable and environment-injected like a store.
Use @Bindable var router = router at the top of body to derive a Binding from it when needed by NavigationStack(path:).
Trigger navigation from any view: router.navigate(to: .destination).
Do NOT use NavigationLink(destination:) for programmatic navigation — use the router instead. NavigationLink is fine for static/declarative links.
Auth session

UserSession is a struct nested logically with AuthStore. Extend it per project.
AuthStore.isAuthenticated is a computed property derived from session != nil — do not store a separate Bool.
Access session data in views via authStore.session?.userId, authStore.session?.email, etc.
Adding new services

Create ServiceName.swift in Services/.
Services should have no dependencies on stores — stores may depend on services, not the reverse.
Mark the service as [REMOVABLE] in both the file header comment and in PLAN.md if it's optional.
Design System

Colors: Always use Color.app* accessors. These are auto-generated by Xcode from the color sets in Assets.xcassets — name new color sets with the App prefix (e.g. AppWarning → Color.appWarning). Never hardcode Color(.red) or hex values in views.
Fonts: Always use Font.app* extensions (defined in Core/DesignSystem/Typography.swift). Never call .font(.headline) directly in views.
Spacing: Always use Spacing.* constants (defined in Core/DesignSystem/Spacing.swift). Never hardcode numeric padding/spacing values in views.
Components

Prefer reusable styles and modifiers for built-in views, such as `ButtonStyle`, `TextFieldStyle`, `LabelStyle`, and custom `ViewModifier`s. Keep visual tokens in `Core/DesignSystem/` and reusable style definitions in `Core/Styles/`.
Use wrapper views in `Core/Components/` only when a view has repeated structure or contains more than styling behavior. When you do create wrappers, prefix them with `App` (e.g. `AppDivider`, `AppSectionHeader`).
Components and styles should accept `LocalizedStringKey` for any user-visible text.
Components and styles must support both light and dark mode using semantic colors from the design system.
Do not add business logic to components or styles. They are pure UI.
Localization

All user-visible text must be a LocalizedStringKey. In Text(...), this is automatic. In components, declare parameters as let title: LocalizedStringKey.
Add new strings to Resources/Localizable.xcstrings. Use dot notation keys: feature.element.descriptor (e.g. login.email.placeholder).
Never hardcode English strings in views.
Logging

Use Logger from OSLog. Do not use print() in committed code.
Loggers are defined in Services/LoggingService.swift as static properties on Logger.
Use the appropriate log level: debug for dev noise, info for normal events, warning for recoverable issues, error for failures, critical for fatal/unexpected states.
Example: Logger.auth.info("Session started for \(email, privacy: .private)")
Mark sensitive data with privacy: .private or privacy: .sensitive.
SwiftData [Optional module]

If SwiftData is in use, all models live in SwiftData/Models/.
The ModelContainer is configured in SwiftData/AppModelContainer.swift and injected in the App entry point.
Do not access ModelContext directly in views — use a service or store that holds the context.
File & Naming Conventions

Files: PascalCase.swift
Types: PascalCase
Variables/functions: camelCase
Constants: camelCase (inside enums or as static let)
Group names and folder names must match exactly (Xcode "Group with Folder")
Stores: suffix with Store — e.g. AuthStore, ThemeStore
Services: suffix with Service — e.g. LocalStorageService
Views: suffix with View — e.g. LoginView, SettingsView. Exception: App-prefixed components.
What NOT to Do

Do not install Swift packages without explicit instruction from the developer.
Do not use EnvironmentObject — it is superseded by @Observable + @Environment.
Do not use @StateObject or @ObservedObject — superseded by @Observable.
Do not put business logic in views. Move it to a store or service.
Do not use UIKit APIs unless there is no SwiftUI equivalent. If you must, wrap it in a UIViewRepresentable.
Do not use print() for logging.
Do not hardcode colors, fonts, or spacing — always use the design system.
